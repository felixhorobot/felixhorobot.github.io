NEW MOTION PLANNING / TRAJECTORY OPTIMISATION

A 180° U-turn around a wall,
solved as optimal control.

Motion planningPath planningOptimal controlCasADi + IPOPTVehicle dynamics

A truck must make a direct 180° U-turn around a middle wall. I first hand-designed three strategies against steering only: a 2 m swing left before the turn, braking the right-side wheels up to 8% at full lock, and both together. Then I wrote the manoeuvre as an optimal control problem in CasADi and solved it with IPOPT, so the optimiser finds the steer, brake and speed profile itself.

Each optimised run gets the same actuators, the same ground space and the same time budget as its hand run, and the whole truck body must stay clear of the wall. Every answer is re-simulated with RK4 on a 20× finer grid; 10 constraints are checked and none is violated.

Minimise the entry-to-exit gap (or the time) subject to vehicle kinematics, steer, brake and speed limits, the ground boundary and full-body clearance from the middle wall.
Fair comparison
Same actuators, same ground space and same time budget as the matching hand run. Hand runs checked against the wall too: 0.000 m penetration.
Verification
Optimal controls re-simulated with RK4 on a 20× finer grid; a constraint counts as violated if off by more than 1e-4.
Search
Cold start, forced turn-start seeds (X ≥ −3 / 0 / +3 m, then released) and warm starts from the other strategies. The best valid answer is kept.

WHAT I CHANGED, AND WHAT IT BOUGHT

  1. 01 / Data source

    GA ELVIS has no coverage of the mine site, so the surface comes from QldDem LiDAR instead.

  2. 02 / Goal and heuristic

    The original goal, the top of a waste dump at 470 m, cannot be reached under a strict 10% limit: its only ramp is 10–13%. So the goal moved to the 409 m pad, reachable under all three limits. The heuristic now uses the strict grade too, so an unreachable goal is known at the start, not after a 20-minute search.

  3. 03 / Weighted → exact A*

    eps 2 → eps 1. The loaded route went from 278 s to 239 s (14% faster), and the weighted search’s “big detour” turned out to be an artefact.

  4. 04 / Compiled expand

    The node expansion compiled with numba: 215 µs → 33 µs per expand, with identical results.

  5. 05 / Compiled search loop

    The whole search loop in numba: about 35× faster per scenario. Three scenarios in parallel: about 10 minutes → about 16 seconds.

  6. 06 / Parameter sweep

    162 runs on 6 cores picked an 8 m motion primitive over 6 m. Worst gap to the best route found: 3.7% → 0.5%; the empty route is 6 s faster.

NEW AUTONOMOUS HAULAGE / ROS 2 + NAV2 + GAZEBO

Four ways to fail,
then 50 runs without a contact.

ROS 2 JazzyNav2Gazebo HarmonicHybrid A*Residual RL (PPO)ONNX Runtime C++3D lidar

An autonomous haul truck in simulation. It drives the haul road and the ramp, avoids fallen boulders and a patrolling light vehicle, then reverses into the dump bay. The global planner is my own Hybrid A* Nav2 plugin, which respects the Ackermann turning limit. The controller is Regulated Pure Pursuit plus a residual PPO policy: the policy learns a bounded speed and curvature correction, is exported to ONNX and runs inside a C++ Nav2 controller plugin. Nav2’s collision monitor is the independent safety layer on the 3D lidar.

Each clip replays a recorded run (rosbag). Red dots are lidar obstacle points, purple is the local costmap and green is the plan. Each boulder is tagged with the range at which the lidar first saw it, and whether it reached the costmap.

WHAT I CHANGED, AND WHAT IT BOUGHT

  1. 01 / Costmap height

    Nav2’s obstacle layer has its own 2 m height limit in the world frame, and the ramp sits 4–9 m up. Height filtering now happens in the lidar filter, in the truck frame. This fixes clips 1 and 2.

  2. 02 / Lidar self-occlusion

    The placeholder cab box hid the lidar’s low forward rings. With the detailed truck body, boulders are now seen at 28–30 m.

  3. 03 / Balanced buffers

    Obstacle inflation went from 1.5 m to 1.0 m, which leaves room on the berm side of a swerve. Berm grazes: 4/20 → 0/20 (RPP), 1/20 → 0/20 (RL). This fixes clip 3.

  4. 04 / Parking acceptance

    The truck now parks to the spec (< 0.15 m, < 3°, stopped 3 s) instead of chasing Nav2’s tighter goal check. Every run finishes within 0.092 m / 2.85°. This fixes clip 4.

  5. 05 / Residual RL

    PPO learns a bounded correction on top of Pure Pursuit. It runs as ONNX in a C++ Nav2 plugin, at 0.06 ms p50 and 0.14 ms p99. Missions are 14% faster (155 s vs 181 s), still with 0 collisions.

  6. 06 / Hybrid A* plugin

    The planner is curvature-limited to the Ackermann turn. Planning takes 11 ms median and 20 ms p95 on the mine map, and every smoothed segment stays within the steering limit.

How the K-code OCR got to 100%: three pivots 80% → 97% → 100% ＋
01 / Whole code → single characters

Problem. EasyOCR and PaddleOCR read the code as one word; any unseen combination failed, about 80% and falling.

Fix. Read one character at a time on a custom set of 2,000+ single characters.

Result. 97% per character; new combinations no longer matter.

02 / Reuse the tally crops

Idea. The counting model already boxes every board face; slice those boxes to find the stamp.

Result. Finds the code every time, but a single board reads at only about 50%. Not enough alone.

03 / The K anchor

Problem. Boards are often upside down; a flipped 2 reads as a 5, so voting across boards failed and orientation models overfit (64%).

Fix. Every code starts with K. Train K in all four rotations and use it to right the board before reading.

Result. Orientation 100%; voting across 70 righted boards gives the 100% pack read.

06 ROOT CAUSE ACROSS THE STACK

135 ms to 20 ms.
Traced to the GPU memory clock.

ProfilingLog analysisGPU power states

Production, August 2026. Two trigger-mode cameras in VisionPLC went from their usual 40–80 ms to 128–137 ms per inference. The platform average of 20–35 ms is a different measure; these two cameras only run when the PLC trigger fires.

  1. 01 / Clear the obvious suspect

    The newest change was a blur-detection feature, so it was blamed first. Two facts cleared it: the feature was switched off, and its code was newer than the process that was running slow, so that process had never loaded it.

    A suspect is cleared by evidence, not by opinion.

  2. 02 / Read the logs, then the hardware

    The logs showed an always-on model had been removed some time before. It had been doing two quiet jobs: feeding the health watchdog (without it the process was force-restarted every minute) and keeping the GPU busy.

    Idle, the GPU dropped to power state P8 and its memory clock fell from 13,801 MHz to 405 MHz, a 34× drop. YOLO inference is memory-bandwidth bound, so every trigger paid the wake-up cost.

  3. 03 / Fix by measurement

    A keep-alive dummy inference inside the existing 100 ms poll loop, only when idle for more than 0.25 s. Real frames suppress it and its results are never forwarded, which keeps the watchdog honest. The dummy frame must be full size: a 160 px frame only got to 111 ms.

Keep-alive rateInferenceNote
None131.6 and 137.1 msThe regression, one value per camera
1 / sUnstable
4 / s18.9 msChosen
10 / sNo betterNo gain over 4 / s
4 / s, 160 px frame111 msThe dummy frame must be full size

Result: 131.6 → 22.1 ms and 137.1 → 19.6 ms, for about 10 W and 6% GPU. Faster than the system had ever run, because the keep-alive warms the real counting model, which the old always-on model never did.

FIVE THINGS I TELL EVERY PLANT MANAGER BEFORE WE TALK MODELS

I know what ML can do, and what it cannot. That decides where it goes. ＋

Example. A classifier will tell you a board is skewed with 0.94 confidence; it will not tell you why, and it will be wrong on a frame it has never seen. So on the infeed the model raises the flag, the PLC interlocks still own the stop, and every mismatch is logged for retraining. Confidence is a signal to act on, not a guarantee, and the system is designed around that.

Machine vision: we set the rules. Machine learning: the model finds patterns humans cannot even notice. ＋

Example. With machine vision we tell the system an orange is orange in colour and round in shape, and it checks those two rules. With machine learning we only annotate: this is an orange, this is not. The model works out for itself which combinations of texture, shading, edge and colour separate them, including patterns we never wrote down.

Dataset quality matters more than algorithm selection. ＋

Example. The residual counting misses on the pack line were not fixed by a bigger model. They were traced to edge conditions missing from the training data, then closed by collecting exactly those frames. Same YOLO, better data, 99% tally.

A stable environment gives consistency. ＋

Example. Fixed camera position, fixed working distance, controlled lighting and a PLC trigger that fires at the same point every pack. Once the frame is the same every time, the model only has to learn the product, not the plant.

The model is only deployed when the PLC acts on it. I do that side too. ＋

Example. Most manufacturing runs on PLCs. I write the Rockwell Studio 5000 logic that turns an inference result into a stop, alarm or setpoint, and I fit out the hardware around it: the electrical cabinet, 24 V power supply, MCBs, network switch and PoE for the cameras. For a customer that means one person commissions the camera, the model and the control loop, with no hand-off between vendors.

TWO HABITS

Imperfect data is my normal data. Grain, knots, wet vs dry, pale to black ＋

Mismatch records. Every output that disagrees with the expected value is kept for review and retraining. Residual counting misses were traced this way to edge conditions absent from training data, then closed with targeted collection.

Material decides the sensor. Laser misread dark and wet timber, so a feedback sensor became ultrasonic, with its slower response handled in the PLC logic.

Optics from first principles. FOV from working distance and target size, checked against manufacturer specs, checkerboard calibration, lighting and position tuned per install.

Signal from the sensor stream. A proximity sensor or a drive signal triggers inference, so the model only sees the frames that matter. Augmentation is set per task (flip, HSV, scale, mosaic), with synthetic OCR-A fill for rare characters.

Models earn the right to run. Acceptance criteria → test set → live trial ＋

Acceptance criteria are set by the goal before work starts. Pilots run on small datasets; a test set is kept aside with mAP, precision and recall targets; then a live trial on the line before sign-off and an operator feedback loop into retraining. Monitoring stays on after go-live: the data-monitoring dashboard and the mismatch records are the continuous-iteration engine.
