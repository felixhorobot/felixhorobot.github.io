What I bring as a Computer Vision Specialist

Five things I tell every plant manager before we talk models

▾I know what ML can do, and what it cannot. That decides where it goes.

Example. A classifier will tell you a board is skewed with 0.94 confidence; it will not tell you why, and it will be wrong on a frame it has never seen. So on the infeed the model raises the flag, the PLC interlocks still own the stop, and every mismatch is logged for retraining. Confidence is a signal to act on, not a guarantee, and the system is designed around that.

▾Machine vision: we set the rules. Machine learning: the model finds rules and patterns humans cannot even notice.

Example. With machine vision we tell the system an orange is orange in colour and round in shape, and it checks those two rules. With machine learning we only annotate: this is an orange, this is not. The model works out for itself which combinations of texture, shading, edge and colour separate them, including patterns we never wrote down.

▾Dataset quality matters more than algorithm selection.

Example. The residual counting misses on the pack line were not fixed by a bigger model. They were traced to edge conditions missing from the training data, then closed by collecting exactly those frames. Same YOLO, better data, 99% tally.

▾A stable environment gives consistency.

Example. Fixed camera position, fixed working distance, controlled lighting and a PLC trigger that fires at the same point every pack. Once the frame is the same every time, the model only has to learn the product, not the plant.

▾The model is only deployed when the PLC acts on it. I do that side too.

Example. Most manufacturing runs on PLCs. I write the Rockwell Studio 5000 logic that turns an inference result into a stop, alarm or setpoint, and I fit out the hardware around it: the electrical cabinet, 24 V power supply, MCBs, network switch and PoE for the cameras. For a customer that means one person commissions the camera, the model and the control loop, with no hand-off between vendors.

▾How it is builtHow it is builtPython · PySide6 · YOLO v8-v11 · TensorRT/ONNX · pycomm3 · Flask · SQLite
  • Isolation. Capture per camera on QThreads; YOLO in its own process so CUDA never shares the GUI. Frames cross via SharedMemory, zero copy.
  • Trigger. Polls a PLC tag, fires on rising edge, cooldown, N-of-M temporal gating, then writes count, boolean or threshold to the output tag.
  • OCR chain. Stamp detection, orientation, projection-valley character split, per-character YOLO classify, vote across boards for the winner.
  • Resilience. RTSP reconnect, offline watchdog, SHA256 model validation, atomic config saves, GPU keep-alive, auto-start as a scheduled task. Two shifts, 20 h/day, 5 days.
  • Visibility. Trigger frames archived with 1 GB volume management, SQLite metrics, shift statistics, Flask dashboard with Normal, Permanent and Admin logins scoped per camera.
▾How the K-code OCR got to 100%: three pivots80% → 97% → 100%
1 · whole code → single characters

Problem. EasyOCR and PaddleOCR read the code as one word; any unseen combination failed, about 80% and falling.

Fix. Read one character at a time on a custom set of 2,000+ single characters.

Result. 97% per character; new combinations no longer matter.

2 · reuse the tally crops

Idea. The counting model already boxes every board face; slice those boxes to find the stamp.

Result. Finds the code every time, but a single board reads at only about 50%. Not enough alone.

3 · the K anchor

Problem. Boards are often upside down; a flipped 2 reads as a 5, so voting across boards failed and orientation models overfit (64%).

Fix. Every code starts with K. Train K in all four rotations and use it to right the board before reading.

Result. Orientation 100%; voting across 70 righted boards gives the 100% pack read.

03 · Daemon AI platform · 9 cameras · anomaly detection

Skew, tangle and auto-feed on the log infeed

Classification models on the infeed chains at up to 120 boards a minute. Skew or Tangle stops the drive chain through the Rockwell PLC before a blockage; Normal lets it run. On the log deck a log-gap class runs the chain and a pocket-fill count drives auto feeding. Before any of it, the work was reading the existing Studio 5000 program: the tags, the drive references and the interlocks already in place, then deciding where an ML output can safely enter that logic. Cameras selected and installed, models trained, control logic written by me. Operators only monitor.

How I work

Three habits, expand any of them

▾Imperfect data is my normal datagrain, knots, wet vs dry, pale to black

Mismatch records. Every output that disagrees with the expected value is kept for review and retraining. Residual counting misses were traced this way to edge conditions absent from training data, then closed with targeted collection.

Material decides the sensor. Laser misread dark and wet timber, so a feedback sensor became ultrasonic, with its slower response handled in the PLC logic.

Optics from first principles. FOV from working distance and target size, checked against manufacturer specs, checkerboard calibration, lighting and position tuned per install.

▾Root cause, found by measurement135 ms → 20 ms, traced to the GPU clocks

A stage-by-stage timing pipeline benchmarks preprocessing through inference, so the bottleneck is found by measurement. When two trigger cameras drifted from 40-80 ms to about 135 ms, the obvious suspect was cleared by evidence. The logs pointed at a removed always-on model that had kept the GPU memory clock pinned; idle it fell from 13,801 MHz to 405 MHz, a 34x drop, and YOLO is memory-bandwidth bound.

Fix: a keep-alive inference through the real model, tuned by measurement. 1/s unstable, 4/s gave 18.9 ms, 10/s no further gain. 131.6 ms down to 22.1, for about 10 W.

▾Models earn the right to runacceptance criteria → test set → live trial

Acceptance criteria are set by the goal before work starts. Pilots run on small datasets; a test set is kept aside with mAP, precision and recall targets; then a live trial on the line before sign-off and an operator feedback loop into retraining. Monitoring stays on after go-live: the Data Monitoring dashboard above and the mismatch records are the continuous-iteration engine.

04 · Kaggle · RSNA 2026 Knee Abnormality Detection · research

Reading knees without labels

Predict 12 knee abnormalities from MRI when only 58 of 4,407 studies carry human labels. An LLM reads every radiology report (9+ languages) into a 6-state judgment with calibrated probability and quoted evidence; a second LLM pass averaged in lifts the label ceiling to 0.906. DINOv2 ViT-S over 32 slices in 3 planes, 5-fold ensemble: AUC 0.903, above its own teacher's noise. The 58 gold studies are a thermometer, never fuel.
